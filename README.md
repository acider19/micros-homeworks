# Решение: Введение в микросервисы

## Выгоды перехода на микросервисную архитектуру

### Независимость деплоя

Каждый микросервис разворачивается и обновляется сам по себе. Команда по заказам может выпускать новую версию своего сервиса, не дожидаясь, пока команда по каталогу товаров закончит свою работу. Time-to-market сокращается, а риск сорвать весь релиз из-за одного бага в другом сервисе падает.

### Масштабирование по требованию

В чёрную пятницу нагрузка на каталог товаров выросла в 10 раз? Достаточно поднять ещё инстансов каталога. В монолите пришлось бы тащить за собой всё приложение целиком, потребляя ресурсы на тех компонентах, которые даже не нагружены.

### Технологическая свобода

Каталог товаров можно написать на Python, систему заказов на Go, а рекомендательный движок на Java. Каждая команда выбирает стек, который подходит именно ей.

### Изоляция сбоев

Падение сервиса рекомендаций не должно обрушить процесс оформления заказа. В монолите panic в одном модуле уронит всё приложение.

### Командная автономия

Каждая команда владеет своим сервисом от дизайна до деплоя. Принимать решения становится проще, ответственность становится яснее.

### Масштабирование команд

Бизнес растёт, и новые команды подключаются к новым сервисам, не конфликтуя с существующими. В монолите 50 разработчиков на одном репозитории — это хаос.

## Проблемы, которые нужно решить в первую очередь

### Распределённые транзакции

В монолите есть `BEGIN TRANSACTION`, и несколько таблиц обновляются атомарно. В микросервисах каждый сервис живёт со своей базой. Чтобы как-то это координировать, понадобятся паттерны вроде Saga (хореография или оркестрация), Event Sourcing для восстановления состояния и компенсирующие транзакции для отката при ошибках.

### Межсервисное взаимодействие

Тут нужно определиться: синхронный вызов (REST или gRPC, для запрос-ответ) или асинхронный (очереди сообщений вроде Kafka или RabbitMQ, для event-driven архитектуры). И на входе всего этого обязательно понадобится API Gateway для маршрутизации и аутентификации.

### Наблюдаемость (Observability)

Без централизованного сбора логов (ELK/EFK-стек), метрик (Prometheus + Grafana) и распределённой трассировки (Jaeger или Zipkin) в микросервисной архитектуре делать нечего. Когда запрос проходит через десяток сервисов, найти проблему без инструментов невозможно.

### Деплой и оркестрация

Контейнеризация (Docker), оркестрация (Kubernetes), CI/CD пайплайны для каждого сервиса и, возможно, Service Mesh (Istio, Linkerd) для управления трафиком. Без этого каждый деплой превращается в квест.

### Управление данными

Каждый сервис — своя база данных (Database per Service). Значит, нужна синхронизация данных между сервисами, а также репликация и шардирование для производительности.

### Тестирование

Интеграционные тесты распределённой системы, контрактное тестирование (Pact) и нагрузочное тестирование (k6, Locust). Писать их сложно, но без них неприятности на проде гарантированы.

---

## Вывод

Для крупного интернет-магазина переход на микросервисы — это реальная возможность получить масштабируемость и независимость команд. Но начинать лучше поэтапно: берём пилотный проект на одном-двух сервисах и постепенно разбираемся с распределёнными транзакциями, мониторингом и оркестрацией.
