## Задача 1: Обеспечить разработку (GitLab CI/CD)

### Архитектура

```
[Разработчик] ──git push──► [GitLab (облако)]
                                  │
                                  ├── Git-репозитории (1 репо на сервис)
                                  ├── .gitlab-ci.yml (конфигурация пайплайна)
                                  └── CI/CD Runners
                                       │
                                       ├── Shared Runners (облачные)
                                       └── Private Runners (собственные серверы)
                                            │
                                            └── [Docker Registry]
```

### Соответствие требованиям

| Требование | Реализация |
|-----------|-----------|
| Облачная система | GitLab.com в облаке или собственный GitLab на своих серверах |
| Git | Используем Git — систему контроля версий |
| Репозиторий на каждый сервис | Один проект — один микросервис |
| Запуск по событию | Пуш в репозиторий запускает сборку автоматически |
| Запуск по кнопке с указанием параметров | Ручной запуск с указанием параметров |
| Настройки для каждой сборки | Настройки в `.gitlab-ci.yml` и переменных окружения |
| Шаблоны для различных конфигураций | Готовые шаблоны через `include` — не нужно дублировать код |
| Безопасное хранение секретных данных | Пароли и ключи маскируются и защищены от просмотра |
| Несколько конфигураций для сборки из одного репозитория | Несколько пайплайнов: разные ветки, матричные сборки |
| Кастомные шаги при сборке | В задачах сборки можно писать свои скрипты |
| Свои Docker-образы для сборки проектов | Собственные Docker-образы для сборщиков |
| Агенты на своих серверах | GitLab Runner — ставится на любые свои серверы |
| Параллельный запуск нескольких сборок | Сборки запускаются параллельно и могут зависеть друг от друга |
| Параллельный запуск тестов | Тесты бегают параллельно с подробным отчётом |

### Конфигурация

- [.gitlab-ci.yml](src_1/.gitlab-ci.yml)

### Обоснование выбора

GitLab закрывает всё: хранение кода, сборку, хранение образов, безопасность. Свой сборщик можно поставить на любые серверы. Матричные сборки позволяют собирать для разных ОС и версий параллельно. Auto DevOps сам определяет язык и настраивает пайплайн.

## Задача 2: Логи (Fluent Bit + Elasticsearch + Kibana)

### Архитектура

```
[Сервисы (stdout)] ──► [Fluent Bit (DaemonSet)] ──► [Elasticsearch] ──► [Kibana :5601]
```

### Выбор компонентов

| Компонент | Роль | Почему выбран |
|-----------|------|---------------|
| Fluent Bit | Сбор логов | Легковесный (менее 1 МБ памяти), работает на каждом сервере, собирает stdout контейнеров |
| Elasticsearch | Хранение и индексация | Мощный полнотекстовый поиск, легко масштабируется, хранит структурированные данные |
| Kibana | Веб-интерфейс для анализа | Графики, визуализация, сохранённые поиски, ссылки на фильтры |

### Соответствие требованиям

| Требование | Реализация |
|-----------|-----------|
| Сбор логов со всех хостов | Fluent Bit запускается на каждом сервере и собирает все логи |
| Минимальные требования к приложениям | Приложения просто пишут в stdout — Fluent Bit подхватывает всё автоматически через формат контейнера |
| Гарантированная доставка логов | Логи буферизуются на диске, при ошибках — повторные попытки с нарастающей задержкой |
| Поиск и фильтрация по записям логов | Elasticsearch обеспечивает полнотекстовый поиск и фильтрацию |
| Пользовательский интерфейс для разработчиков | Kibana — веб-интерфейс для поиска и просмотра логов |
| Сохранённый поиск по записям логов | В Kibana можно сохранить запрос и поделиться ссылкой |

### Конфигурация

- [fluent-bit.conf](src_2/fluent-bit.conf)
- [docker-compose.yaml](src_2/docker-compose.yaml)

## Задача 3: Мониторинг (Prometheus + Grafana)

### Архитектура

```
[Сервисы /metrics] ──► [Prometheus (pull)] ──► [Grafana :3000]
       │                      │
       │                      ├── Recording Rules
       └── [Node Exporter]    └── Alertmanager
```

### Выбор компонентов

| Компонент | Роль | Почему выбран |
|-----------|------|---------------|
| Prometheus | Сбор метрик | Сам подтягивает метрики, PromQL для запросов, автоматическое обнаружение сервисов, нативная интеграция с Kubernetes |
| Grafana | Визуализация метрик | Красивые графики, оповещения, шаблоны, можно делиться дашбордами |
| Node Exporter | Метрики хостов | Процессор, память, диски, сеть — стандарт для сбора метрик хостов |

### Соответствие требованиям

| Требование | Реализация |
|-----------|-----------|
| Метрики со всех хостов | Node Exporter устанавливается на каждый сервер |
| CPU, RAM, HDD, Network хостов | Собирает данные о процессоре, памяти, дисках и сети |
| Метрики потребления сервисов | cAdvisor следит за потреблением ресурсов каждым контейнером |
| Специфичные метрики сервисов | Каждый сервис выставляет свои метрики через `/metrics` (счётчики, гистограммы) |
| UI с запросами и агрегацией | Grafana позволяет интерактивно запрашивать и агрегировать метрики |
| Настройка dashboards | В Grafana можно собирать дашборды перетаскиванием панелей, настраивать шаблоны и переменные |

### Конфигурация

- [docker-compose.yaml](src_3/docker-compose.yaml)
- [grafana-dashboard.json](src_3/grafana-dashboard.json)
